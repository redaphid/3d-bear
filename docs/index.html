Stage one · reference images · Z-Image Turbo · 896² · 8 steps

Twenty

bears in

six minutes

Reconstruction models are ruthless about their input. Stage one decides everything downstream, so the first job was a bear that stands three-quarter to the camera: whole animal, flat grey ground, no shadows, matte clay, no fur to reconstruct.

Round one asked Qwen-Image 2512 for a “three-quarter front view” and got four bears staring dead ahead. The model centres and symmetrises unless the view is described geometrically, and early in the prompt. So the prompt became a matrix built in-graph from six clauses: subject, view, pose, mass, mouth, style. The view clause stopped naming an angle and started describing where the shoulders are.

Then the sweep moved from Qwen to Z-Image Turbo, twenty candidates in one graph, five per chunk, and the whole sheet was on the table in about six minutes.

Stage two · image to 3D · rembg · Hunyuan3D 2.1

66

From picture to solid

Sixty-six seconds from one cutout to a mesh: 271,556 triangles, not watertight, winding inconsistent. Repair is a real stage, not a checkbox. But the geometry it invents is right.

The fear going in was a flat back. A single front-facing photograph carries no information about the far side, and a reconstruction that fakes it badly gives you a bear-shaped relief. From a dead-on frontal reference, Hunyuan3D 2.1 invented a plausible bear behind the bear: shoulders, spine, rump. The raised forelegs read correctly from every side. Multi-view input was never needed for this pose.

Without background removal

A 160 × 47 mm

The control run skipped the cutout and fed the flat grey ground straight into the reconstruction. Hunyuan3D did exactly what it was asked: it rebuilt the backdrop as a solid slab and attached the bear to it as a relief. 879,874 triangles of wall.

Background removal is mandatory, not a nicety. Every one of the twenty goes through rembg first.

wall

The sweep verdict

Octree 256, 384 and 512. Thresholds 0.5, 0.6, 0.7. Two more seeds. Fifty steps instead of thirty. All on the same reference, all at 160 mm, all rendered six ways. Same silhouette, same back, footprint within 0.3 mm, and the same three places needing support: underarms, crotch, under the muzzle.

It is all the same bear

At print scale the 0.6 mm voxel remesh discards everything above octree 256 anyway. Settings for the twenty: octree 256, 30 steps, threshold 0.6, any seed.

Twenty reconstructions one queue

Every reference was reconstructed, not just the picks. A mesh is what you actually choose on; picking from the picture alone hides the failure modes. Red marks faces that would need support.

Stage three · printable mesh · trimesh + manifold3d

874shells

to

1solid

Euler number 349 → 2 · watertight yes · winding consistent · manifold3d NoError · 5,876 faces at 0.6 mm pitch · about eight seconds

Making it real. What comes out of the reconstruction is marching-cubes soup: one connected body, about 180 boundary loops, 873 shells of debris, non-manifold edges from self-intersections. Hole filling cannot fix it by construction.

The repair is volumetric. Voxelise the soup into a solid at a 0.6 mm pitch, re-extract the surface, and the result is watertight by definition. Then decimate, orient, scale to 160 mm, and cut 8 mm off the bottom so the base is open for the light and the pole. Support need fell from 8.7 % to 6.2 % on the first bear; what remains is the crotch, the underarms and under the muzzle, which is a pose question, not a repair one.

How many faces does a jaw need?

Low-poly facets catch the ultraviolet nicely, so fewer faces is not only smaller. But 6,000 collapses the open mouth to a slit. 12,000 keeps it. That is the default.

How it was built · fragments · blueprints · sweeps

The pipeline is a program

Not a sequence of manual ComfyUI sessions. Fragments are functions, blueprints are programs, and every stage is a sweep of twenty that lands on a contact sheet. Nobody waits for a human. The GPU never idles: the next informative job is queued behind the current one, and picks happen with full information, by id, once it exists.

Everything ran locally on one card, with no partner nodes and no per-generation billing anywhere in the pipeline. Parallel agents owned disjoint files; one of them committed.

  1. Reference images

    Twenty prompts from one six-clause matrix, one graph, five per chunk.

    • Z-Image Turbo, 8 steps
    • Qwen-Image 2512 for finalists
    • prompt_builder fragment
    • sheet.py contact sheet

  2. Image to 3D

    Cut out, then reconstruct all twenty at the settings the sweep chose.

    • rembg
    • Hunyuan3D 2.1, octree 256
    • mesh_views.py six views

  3. Printable mesh

    Voxel remesh, validate, decimate, orient, scale, open the base.

    • trimesh + manifold3d
    • mesh_repair.py, 0.6 mm pitch
    • support census at 45°

  4. Glowing print

    Hollow, two walls, no floor, a blacklight inside, a pole below.

    • Centauri Carbon 2
    • 0.6 mm hardened nozzle
    • strontium-aluminate PLA

  • Fragments are functions

    A few nodes with typed inputs, outputs and named params. t2i, rembg, hy3d_i2m, tap_image. Composed, never copy-pasted.

  • Blueprints are programs

    A YAML file wires fragments; foreach runs the whole pipeline once per item inside one graph so ComfyUI parallelises the branches.

  • Sweeps of twenty

    Every stage produces about twenty candidates and a contact sheet. Picks happen with full information, by id, not before it exists.

  • Taps, bypassed by default

    Intermediate saves live in the graph and are stripped at build time. Un-bypass one in the browser and only it runs; everything upstream is a cache hit.

  • Outputs are a library

    Every PNG and GLB carries the API prompt that made it. Drag a file onto the canvas and the exact graph comes back.

  • One graph, watched live

    The compiled graph is laid out grouped and colour-coded on the browser canvas with live denoising previews, so the sweep is something you can watch.

Overnight, 9 to 10 September · war stories

The night the box nearly went down

  1. 1 / 45 min

    Weights streaming from RAM

    Two Ollama runners were squatting on 6.2 GB of the 4090. Qwen-Image 2512 needs about 20 GB, so it streamed weights from system memory: one image every forty-five minutes.

  2. 161 / 163 GB

    The commit limit

    ComfyUI's Python reached 47 GB of commit beside a 62 GB WSL VM. The machine hit its limit and the Claude Code session died. Windows stayed up. Stage one moved to Z-Image Turbo.

  3. 157.8 GB

    The guard fires

    A memory guard written after the crash watched system commit during the reconstruction queue. It fired once, at 157.8 GB, and saved the box.

  4. 7+ min

    A decode that ignored interrupt

    With the unet and text encoder both resident, one branch's VAE decode sat at 100 % GPU with no progress. Interrupt never reaches a decode. Fix: text encoder on the CPU, 12.7 GB peak, 33 s per image.
